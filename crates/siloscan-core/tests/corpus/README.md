# Detection corpus

A committed, versioned body of realistic files that the shipped rule pack is
measured against. `tests/detection_corpus.rs` is the harness: it materializes
this tree, scans it with the default pack, and turns the result into two
numbers.

The corpus exists because the generic rules in `rules/default/generic.yaml`
were written and then tuned against no corpus at all. Four regexes were judged
by reading them. The 1.4.1 gate found, among other things, that an allowlist
pattern dropped every credential exactly forty characters long, that any
password containing `!` or `(` was structurally undetectable, and that the
canonical `scheme://:password@host` form was never reported. None of those
survive a measurement. That is the whole argument for this directory.

## Layout

    tree/            the corpus itself, one directory of realistic files
    manifest.tsv     the expectation table, one row per measured line
    README.md        this file

`crates/siloscan-core/Cargo.toml` carries `exclude = ["tests/corpus/**"]`, so
none of this is packaged into the published crate. It is test material and
belongs in the repository, not in every consumer's vendor directory. Verify
with `cargo package --list -p siloscan-core`: the corpus must not appear, and
`rules/default/*.yaml`, `LICENSE`, `NOTICE` and `README.md` must.

## What is in `tree/`

Configuration and source in the shapes credentials actually leak in: `.env`,
`docker-compose.yml`, `application.properties`, `settings.py`, `config.yml`,
`appsettings.json`, `web.config`, `Dockerfile`, a Kubernetes manifest,
`package-lock-excerpt.json`, `.js`, `.go`, `.java`, `.rb`, `.tf`, a GCP service
account JSON, and PEM key files.

Every line that is a test case is either a **positive** the pack must report or
a **negative** it must leave alone. Positives cover vendor-prefixed tokens (AWS,
GitHub in five variants, GitLab, Slack, Stripe, npm, DigitalOcean, Cloudflare,
SendGrid, Mailgun, Twilio, Azure, OpenAI, Anthropic, GCP, JWT, private keys in
four formats) and, more importantly, the generic shapes underneath them:
passwords at nine lengths and five character classes, base64 and base64url
tokens including exactly forty characters, hex secrets at 32, 40 and 64,
credentialed URLs including empty-username forms, `Authorization` headers in
six languages, XML `<password>` elements and .NET `appSettings value=`.
Negatives cover placeholders, environment lookups, template interpolations,
git shas, UUIDs, checksums, inline images, minified identifier soup, English
prose, semantic versions and dotted references.

## No file here spells a credential

Every credential value is a `{{KIND_PARAM_TAG}}` marker on disk. The harness
substitutes it at run time: vendor prefixes are assembled from `concat!` halves
in `detection_corpus.rs`, and the entropy-bearing tail of each value is
generated by a seeded SplitMix64 keyed by the marker's own name. The values are
deterministic - the same marker yields the same value on every platform and
every run - and they exist only in the test process.

This is not decoration. A repository that spells credential-shaped literals is
rejected by GitHub push protection, and a published crate carrying them trips
every consumer's scanner. Two tests hold the line:
`no_corpus_file_spells_a_credential` scans the corpus files and requires zero
findings, and `every_credential_marker_resolves` requires that no marker
survives substitution, so a typo cannot quietly turn a positive into a line
nothing could ever report.

### The marker itself has to be inert

A marker is a run of characters sitting exactly where a credential goes, so it
is a credential shape unless the delimiter makes it one no rule can describe.
The delimiter is braces because `{` sits outside every value class in the pack,
generic and vendor alike. That is a property of the character, not of an
allowlist entry someone may re-argue later, and it holds for the vendor rules
too - those are translated wholesale from an upstream document and regenerated
on every bump, so nothing can be hand-edited into them to stand down on a
delimiter of ours.

The delimiter was `@@NAME@@` first, and that is what the argument is worth. `@`
is a value character in the generic rules, which made `DB_PASSWORD=@@PWA_8_1@@`
an eleven-character value at entropy 2.55, over the 2.5 floor: a release binary
reported 61 findings on this repository's own tree. Allowlisting `@@NAME@@` in
the four generic rules took that to 2, and the last 2 were
`secrets.curl-auth-header` - a translated rule, unreachable from an allowlist,
whose value class admits `@` and `_`. Braces take it to 0 without the pack's
help.

`no_corpus_file_spells_a_credential` scans the files as they sit on disk, with
no substitution and no redaction, and requires zero findings. Anything else
measures a file nobody has.

The corpus also carries template interpolations in the same brace shape -
`{{ .Values.database.password }}` is one of the negatives - so `materialize`
tells the two apart by the name: a marker is upper case, digits and
underscores, and anything else in braces is left verbatim.

## Adding a case

1. Append the line to the right file under `tree/`, using a `{{KIND_PARAM_TAG}}`
   marker wherever a credential goes. `KIND` picks the generator (see
   `credential()` in `detection_corpus.rs`), `PARAM` is its length where a
   length applies, and `TAG` is any integer that makes the marker unique.
   Appending rather than inserting keeps the line numbers of every existing row
   correct.
2. Add a row to `manifest.tsv`: path under `tree/`, 1-based line number,
   expectation, justification. Rows are sorted by path then line.
3. Run the harness. `the_corpus_and_its_manifest_agree` fails if the row points
   at a line that does not exist or repeats one already claimed.

Expectations are one of:

- `NONE` - nothing may be reported on this line.
- `ANY` - exactly one rule must report it, and which one owns the shape is the
  rule author's decision. Use this for generic shapes, so that splitting or
  renaming a generic rule is not a test failure.
- a rule id, or several joined by `|` - one of those rules must report this
  line, and nothing outside the set may. Use this for vendor formats, where a
  specific rule exists and must be the one that fires.

Several ids say every one of them is an acceptable owner of the shape. They do
not license a second report: a line the pack genuinely reports twice names both
ids and argues it in the justification. Five rows do, and all five are the
three structural overlaps `default_pack.rs` records.

Every row carries a justification. A row without one is a case nobody can
argue with later, which is how the current rules were arrived at.

## The floors

    cargo test -p siloscan-core --test detection_corpus

`detection_recall_meets_its_floor` and `detection_precision_meets_its_floor`
print the full list of misses, spurious hits and findings on lines the manifest
does not classify, then assert:

- **recall** - positives reported / positives - at or above `RECALL_FLOOR`.
- **precision proxy** - negatives left alone / negatives - at or above
  `PRECISION_FLOOR`, which is 1.0. Every negative is justified individually, so
  one spurious hit is one defect.

### What the floors do not measure

Both numbers are computed per line and are satisfied by the first matching id,
so neither can see one credential reported twice: a line reported by two rules
is reported, and recall counts it once. That property is held separately, by
`no_measured_line_carries_an_unaccounted_rule`, which fails when a measured
line carries any id its manifest row does not account for - a second id under
`ANY`, or any id outside the set under an explicit list.

Findings on lines with no manifest row at all are printed by `unclassified()`
and are not a failure: a rule may legitimately report a line the corpus does
not measure. There is one, `service-account.json:4`, a 40-hex
`private_key_id`, and whether a GCP key identifier is a credential is a
decision nobody has made in the manifest yet.

`the_pack_reports_three_credentials_twice_and_no_others` in
`crates/siloscan-core/src/default_pack.rs` still holds the same statement from
the other side, one line per overlap, against a synthetic line rather than a
corpus one.

## Rules are measured here before they ship

A change to any file under `rules/default/` is a change to these numbers.
Measure it here, in the same commit, and say what moved. Recall that goes up
while precision goes down is not an improvement, and it is precisely the trade
the 1.4.x generic rules were tuned into blind.

If a negative looks wrong to you, re-argue it in the manifest - change the
expectation and the justification together, in a commit that says why. Do not
delete the row. The row is the record of a decision; deleting it hides that the
decision was reversed.
